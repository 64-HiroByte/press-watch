# `task.md` を使う引き継ぎ

## 目的

長い引き継ぎ内容をプロジェクト直下の `task.md` にまとめ、新しいチャットでも同じ作業範囲と判断条件を共有する。

`task.md` は、実装中に作業範囲や設計判断が変わった場合に修正できる一時的な作業仕様として扱う。

引き継ぎの作成段階では次タスクの詳細設計まで完了させず、何を行うか、なぜ必要か、どこまで扱うかを共有する。

Git では共有しないため、同じローカルリポジトリを使うチャット間の引き継ぎに限って利用できる。

## 他の文書との役割分担

- `task.md`: 現在または次の一タスクに固有の作業仕様、確認事項、制約を置く。
- `docs/tasks.md`: プロジェクト全体のタスクと完了状態を管理する。
- `docs/`: 継続して共有すべき要件、設計、開発手順を置く。
- `notes/`: 学習メモ、質疑で深掘りした内容、設計判断の経緯を置く。

`task.md` だけに、継続して必要な仕様や完了記録を残さない。

## 使用する場面

次のいずれかに当てはまる場合に使う。

- 引き継ぎプロンプトが長くなり、貼り付け後の修正が難しい。
- 実装前に複数の設計案を比較する必要がある。
- 作業中に範囲や除外事項を更新する可能性がある。
- 新しいチャットへ、現在の Git 状態、検証条件、公開操作の権限を正確に渡したい。

作業内容が短く明確で、既存文書だけで開始できる場合は、短い依頼プロンプトでよい。

## 作成前の確認

1. プロジェクトルートと現在の Git 状態を確認する。
2. 既存の `task.md` がある場合は全文を読み、別タスクの内容を不用意に上書きしない。
3. `git ls-files -- task.md` の出力が空であり、`task.md` が追跡済みでないことを確認する。
4. `git check-ignore -v task.md` で、`task.md` が Git の追跡対象から除外されていることを確認する。
5. 除外されていない場合は、リポジトリローカルの `.git/info/exclude` に `task.md` を追加する。
6. チーム全体の規約として共有する判断をしていない限り、この目的だけで `.gitignore` は変更しない。

`task.md` がすでに追跡されている場合は作業を止め、追跡から外すか、管理対象の文書として扱うかをユーザーへ確認する。

`.env`、`.env.*`、認証情報ファイル、秘密鍵ファイルは読まず、内容を `task.md` に含めない。

## 記述する粒度

引き継ぎ時点の`task.md`は、次タスクが調査を始め、必要ならPlanへ進める粒度にする。

既存コードを読めば決められる実装方法、ファイル配置、制約名、テストケース、コマンド、期待する個別のREDは、次タスクで決める。

ユーザーがすでに確定した仕様、変更してはいけない境界、誤ったDB接続や外部操作を防ぐ安全条件は、引き継ぎ時点でも明記する。

正本の内容を重複して転記せず、参照先と今回関係する契約の大筋を示す。

網羅性を理由に仮定の異常系や将来の選択肢を増やさず、次タスクで判断できる余白を残す。

## `task.md` に含める内容

タスクに必要な項目だけを、次の順序を目安に記録する。

1. タスクの目的。
2. 現在の Phase、Phase ブランチ、直前の PR、確認済みの Git 状態。
3. 参照する正本と、すでに確定している契約の大筋。
4. 今回扱う範囲と扱わない範囲。
5. 次タスクで決める事項の見出し。
6. TDD、DB接続、外部操作、Git操作の承認境界。
7. 完了条件と必要な検証の大筋。
8. `docs/tasks.md` を完了扱いにする条件。
9. 最後に報告する内容。

詳細な変更候補ファイル、テストケース、コマンド、期待するREDは、ユーザーが引き継ぎ前に確定した場合、または安全境界を具体化するために必要な場合だけ記録する。

それ以外は、次タスクで資料と既存実装を確認してから提示する。

実行のたびに変わる細かなコマンド出力は残さない。

未確定事項は確定した仕様のように書かず、「要確認」や「案」と明示する。

## 新しいチャットの開始プロンプト

長い作業仕様は貼り直さず、次のような短いプロンプトを使う。

```text
PressWatch の次タスクを進めます。
日本語で応答してください。

リポジトリ:
`/absolute/path/to/press-watch`

最初に次の2ファイルを全文読んでください。
- `/absolute/path/to/press-watch/AGENTS.md`
- `/absolute/path/to/press-watch/task.md`

`task.md` を今回の作業仕様として扱ってください。
現在の Git 状態を確認し、記載された親ブランチと作業ブランチ案が適切か報告してください。
ブランチ作成は私の了承後に行ってください。

設計上の未確定事項、影響範囲の広い判断、複数案の比較が必要なら、実装前に Plan モードへの切り替えを提案してください。
明確で小さな実装は Default モードのまま進めて構いません。

`.env`、`.env.*`、認証情報ファイル、秘密鍵ファイルは読まないでください。
コミット、push、PR作成は、検証結果と全差分の再監査結果を提示し、私の明示的な許可を得てから行ってください。
```

パスは実際のプロジェクトルートを解決した絶対パスへ置き換える。

## 作業中の更新

- ユーザーが確定した範囲変更や設計判断を `task.md` に反映する。
- 仮説や検討中の案は、確定事項と区別する。
- 作業範囲を広げるために、AI だけの判断で `task.md` を書き換えない。
- `task.md` の変更後は、実装、テスト、除外事項との矛盾がないか確認する。
- 長期的に残すべき内容が確定したら、適切な `docs/` または `notes/` に移す。

## タスク完了時

1. 動作確認、テスト、セルフレビューを終える。
2. 完了条件を満たした場合だけ `docs/tasks.md` を更新する。
3. 継続して共有する仕様や手順を `docs/` に移す。
4. 学習メモや判断の経緯を残す必要があれば `notes/` に移す。
5. 次タスクが確定している場合は、ユーザーと内容を確認して `task.md` を次タスク用に置き換える。
6. 次タスクが未定の場合は、残すべき情報と移動先をユーザーと確認し、必要な整理を終えたうえで、ユーザーの了承後に `task.md` を削除する。
7. 将来も同じ方法を使う場合は、`.git/info/exclude` の `task.md` は残してよい。
8. `git status --short --branch`、`git ls-files -- task.md`、`git check-ignore -v task.md` を必要に応じて確認し、`task.md` がコミットや PR に含まれないことを確かめる。

`task.md` の内容をそのまま履歴として保存するのではなく、残す価値がある情報だけを適切な文書へ整理する。
