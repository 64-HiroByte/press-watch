# `task.md` を使う引き継ぎ

`task.md`は、一タスクの作業範囲と判断条件を共有する一時的な仕様とする。
Gitでは共有せず、同じローカルリポジトリを使うチャット間で利用する。
文書の役割分担と秘密情報の扱いは`AGENTS.md`に従う。

## 作成前の確認

- プロジェクトルートとGit状態を確認し、既存の`task.md`があれば全文を読んで別タスクの内容を不用意に上書きしない。
- `git ls-files -- task.md`が空であることを確認する。
  追跡済みなら、追跡から外すか管理対象として扱うかをユーザーへ確認する。
- `git check-ignore -v task.md`で除外を確認し、未設定なら`.git/info/exclude`へ追加する。
- チーム共通の規約にする判断がない限り、この目的で`.gitignore`を変えない。

## 記述する粒度

次タスクが調査を始め、必要ならPlanへ進める粒度にする。

- 確定した仕様、変更禁止の条件、DB接続・外部操作・Git操作の承認条件は明記する。
- 配置、制約名、テストケース、実行コマンド、個別のREDなどは、既に合意済みか安全上必要な場合だけ記録する。
- 正本を重複転記せず、参照先の用途と関係する契約の大筋を示す。
- 最初に読む仕様と、調査・実行時だけ必要な資料を分ける。
- 未確定事項は「案」「要確認」とし、実装方法は次タスクの調査へ委ねる。

仮定の異常系や将来の選択肢、毎回変わる細かなコマンド出力を網羅しない。

## `task.md` に含める内容

必要な項目だけ、次を目安に記録する。

- 目的、現在のPhase、親ブランチ、直前のPR、確認時点のGit状態。
- 参照する正本、確定した契約、今回扱う範囲と除外事項。
- 次タスクで決める事項。
- TDD、実DB、外部操作、Git操作の承認条件。
- 完了条件、必要な検証、`docs/tasks.md`の完了更新条件、最後に報告する内容。

## 新しいチャットの開始プロンプト

詳細仕様を貼り直さず、次を基に依頼する。
パスは実際のプロジェクトルートを解決した絶対パスへ置き換える。

```text
PressWatchの次タスクを進めます。
リポジトリ: `/absolute/path/to/press-watch`

次の2ファイルを読み、task.mdを今回の作業仕様として扱ってください。
- `/absolute/path/to/press-watch/AGENTS.md`
- `/absolute/path/to/press-watch/task.md`

現在のGit状態と、記載された親ブランチ・作業ブランチ案の妥当性を確認してください。
承認条件は上記ファイルに従い、関連資料は今回必要な箇所を参照してください。
設計上の未確定事項や複数案の比較が必要なら、編集前にPlanモードを提案してください。
明確で小さな実装はDefaultモードで進めて構いません。
```

## 作業中の更新

- ユーザーが確定した範囲・設計判断を反映し、AIだけの判断で範囲を広げない。
- 仮説と確定事項を分け、更新後に実装・テスト・除外事項との整合を確認する。
- 継続して共有する仕様・手順は、保存先と理由を示して適切な`docs/`へ反映する。
- 個人の学習・判断の経緯をnotesへ記録するのは、依頼または現在の`task.md`に明示された場合に限る。

## タスク完了時

- 指定された検証とレビューを終え、完了条件を満たした場合だけ`task-update-ja`に従って`docs/tasks.md`を更新する。
- 継続する仕様・手順をdocsへ反映する。
  notesはユーザーの依頼または現在の`task.md`に記録が明示された場合だけ、対応するスキルで更新する。
- 次タスクが確定したら内容をユーザーと確認して置き換える。
- 次タスクが未定なら残す情報と移動先を確認し、必要な整理を終えてから、明示的な了承後に`task.md`を削除する。
- 将来も使う場合は`.git/info/exclude`の設定を残してよい。

状態と追跡・除外設定を必要に応じて確認し、`task.md`をコミットやPRへ含めない。
全文を履歴として保存せず、残す価値のある情報だけ適切な文書へ整理する。
