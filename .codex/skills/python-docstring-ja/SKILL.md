# PressWatch Docstring JA

## 書く対象

Pythonを追加・変更・分割・移動した場合は、対象の関数・メソッド・クラス・dataclassとテストのDocstringを確認する。
新規対象と、責務・入出力・異常系・保証範囲を変更した対象には、実際の契約を説明するDocstringを整える。
内部関数、関数内に定義するコールバック、テストhelperも確認対象とし、短い処理や型ヒントがあることだけを理由に説明を省かない。
既存の説明を移すだけで済ませず、変更後の実装・呼び出し方・assertionと照合する。
名称・書式だけの変更を理由に説明を増やさず、無関係な既存関数・テストへの一括追加は行わない。

## 形式

- 日本語のGoogleスタイルとする。
- 型はシグネチャやフィールドに任せ、`Args`・`Returns`・`Attributes`に重複させない。
- Summaryは「です。」「します。」を避け、名詞止め・体言止め寄りの簡潔な表現にする。
- 各項目の説明末尾に句点を付けない。
- `Args`は引数の役割を示し、コードから読める分岐などの実装詳細を繰り返さない。
  関数・メソッド・helper・コールバックには、`self`・`cls`以外の引数がある場合に記載する。
  型名の言い換えだけにせず、入力の意味や必要な前提を示し、既定値・可変長引数も見落とさない。
- `Returns`には戻り値の意味と、利用側に必要な異常系の扱いを示す。
  値を返す場合は記載し、変更せず返す場合・空値・None・タプルの各要素など、契約にある結果を説明する。
  Noneだけを返す処理では形式的な`Returns`を付けず、必要な副作用を本文に示す。
- generatorは`Returns`の代わりに`Yields`で生成する値と必要な終了処理を説明する。
- 呼び出し側が扱う必要のある例外は`Raises`へ書き、捕捉して戻り値へ変換する失敗を送出例外として記載しない。
- dataclassの各フィールドの役割は、必要に応じて`Attributes`へ書く。

```python
def _parse_heading_date(value: str) -> date | None:
    """報道発表日の見出し文字列から日付を抽出

    Args:
        value: 報道発表日の見出し文字列

    Returns:
        抽出した日付、形式不一致または実在しない日付の場合はNone
    """
```

## テストとhelper

新規テストと保証範囲を変更したテストには、再現条件と実際に保証する振る舞いを短いDocstringで示す。
テスト名の言い換えではなく、例えば「不正な認証情報を含むURLを拒否し、診断に認証情報を残さない」のように条件と結果を説明する。
複数入力をまとめたテストは共通する保証を記述し、検証していない形式や経路まで保証する表現を避ける。
テスト本体の関数・メソッドには`Args`・`Returns`を付けない。
入力を受け取るパラメータ化テストでは、その入力の意味を本文で補う。
helperやfixtureには通常の関数と同じ入出力の基準を適用し、テスト本体の例外を流用しない。
patch対象やcleanupの担当・実行時期など、helperを正しく使うための非自明な前提を確認し、必要なものを説明する。
可変長引数や展開を使うhelperは、何を渡すか迷う場合に短い呼び出し例を添えてよい。
呼び出し例を追加・維持する場合は、現在のシグネチャや呼び出し方と照合する。

## 完了前の確認

変更ファイル内の新規対象・契約を変更した対象・Docstringを修正した対象を確認し、ネストした関数・コールバック・テストhelperの見落としを防ぐ。
Docstringの有無だけでなく、Summary、実際の引数と`Args`、戻り値と`Returns`または`Yields`、必要な副作用・例外、テストのassertionとの一致を確認する。
不足を修正した場合は、同じ変更範囲に同種の不足がないか確認し、修正後の説明を実装と再照合する。
Docstringだけの変更には、説明文への完全一致テストや製品全テストを形式的に追加・実行せず、構造・参照・差分を確認する。
