# PressWatch Notes Index JA

## 目的

`notes/`に蓄積した学習メモを、後から必要な情報へたどり着ける状態に保つ。

詳細説明の置き場所を決め、`notes/README.md`、サブディレクトリの索引、用語集、関連リンク、読む順番を最小差分で整える。

## 使うタイミング

- ユーザーが`notes/`全体の整理、体系化、索引作成、読む順番の見直しを依頼したとき
- 同じ用語や説明がtimeline、topics、usageへ重複している可能性があるとき
- Phase完了時など、複数の新規メモをまとめて見直すとき
- `notes/README.md`やサブディレクトリの索引が、現在のメモ構成を案内できていないとき
- 現在の実装説明と歴史的な記録が混ざり、時制が分かりにくくなったとき
- リンク切れ、参照先の移動、未説明の用語によって読み進めにくくなったとき

## このスキルを使わない作業

- 1つのタスクの学習内容や設計判断を記録するだけなら`presswatch-notes-ja`を使う
- ライブラリ、API、メソッド、コマンドの使い方を追記するだけなら`presswatch-usage-notes-ja`を使う
- 用語1件を用語集へ追加するだけなら`presswatch-glossary-ja`を使う
- Markdownの書式だけを直すなら`presswatch-markdown-style-ja`を使う

## 既存メモの役割

- `notes/timeline/`: 作業日、当時の実装、判断の経緯、検証結果を残す
- `notes/topics/`: 複数タスクで再利用する概念、責務分担、設計判断を詳しく説明する
- `notes/usage/`: ライブラリ、API、メソッド、コマンドの使い方をPressWatchのコードと結び付けて説明する
- `notes/topics/presswatch-glossary.md`: 用語の短い意味と詳細メモへの入口を置く
- `notes/README.md`: `notes/`全体の入口、分類、最初に見るメモ、代表的な読む順番を案内する
- サブディレクトリの`README.md`: 同じテーマのメモが複数ある場合に、範囲と読む順番を案内する

この役割を変える必要がある場合は、既存分類を無断で作り替えず、理由と影響範囲をユーザーへ示す。

## 調査の進め方

最初から`notes/`配下の全本文を読まない。

まずファイル名、見出し、既存索引を確認し、依頼に関係する候補を絞ってから必要な本文を読む。

確認例:

```bash
rg --files notes | sort
rg -n '^#{1,6} ' notes --glob '*.md'
rg -n '検索したい用語' notes --glob '*.md'
```

最初に確認するもの:

1. `notes/README.md`
2. 対象サブディレクトリの`README.md`
3. `notes/topics/presswatch-glossary.md`
4. 対象テーマが現れるファイル名と見出し
5. 重複候補と現在のコードに直接関係する本文

`.env`、`.env.*`、認証情報ファイル、秘密鍵ファイルは読まない。

## 詳細説明の正本を決める

同じ内容が複数ファイルにある場合は、説明の役割に応じて詳しく残す場所を決める。

```text
timeline
  その日に何を実装し、何を判断したか

topics
  複数タスクで再利用する概念や設計判断

usage
  APIやライブラリの具体的な使い方

glossary
  一言の意味と詳細メモへのリンク

README
  全体の入口と読む順番
```

正本以外のメモから説明をすべて消す必要はない。

そのファイルの役割に必要な要点を残し、詳しい説明へのリンクを追加する。

## 重複の判断

次は重複として整理を検討する。

- 同じ目的、前提、コード例、結論を、現在の構成を説明するusage、topics、READMEがそれぞれ長く説明している
- 用語集がusageやtopicsと同じ詳説を持っている
- READMEが個別APIの説明まで抱えている
- 同じテーマの新規ファイルを作ったが、既存ファイルへ追記できる

次は意図のある重なりとして残してよい。

- timelineに当時のコードや判断を残し、usageに現在の使い方を記録する
- READMEや用語集に短い説明を置き、詳細メモへリンクする
- 同じ用語を異なる責務の文脈で短く説明する

文章が似ていることだけを理由に、歴史的記録や必要な導入説明を削除しない。

## 現在と過去を分ける

timelineは当時の事実を残すため、現在のコードと違っても一律に書き換えない。

```text
当時の構成を記録している
  履歴として維持する

現在の構成として説明している
  現在のコードへ合わせる

現在と過去が混同しやすい
  「変更前」「当時」「現在」を明記する
```

現在の挙動を断定する文章は、必要な範囲で対象コードやGit管理対象のdocsと照合する。

未確認の設計案は、実装済みの挙動として書かない。

## 索引と読む順番

`notes/README.md`には全ファイルの一覧を並べず、最初に見る入口と代表的なテーマへの導線を置く。

同じテーマのメモが複数あり、読む順番が重要な場合は、サブディレクトリの`README.md`または既存のテーマ索引を更新する。

読む順番は、可能な限り次の流れにする。

```text
短い用語説明
  ↓
基本概念
  ↓
具体的なAPIやコード
  ↓
PressWatch固有の設計判断
  ↓
時系列の実装記録
```

読者がまだ知らない用語を先に使う場合は、同じ段落で短く補足するか、説明見出しへのリンクまたは「後述」を置く。

リンク先を増やすだけで読み順が分からなくなる場合は、番号付きリストと各メモの一行説明を置く。

## 編集方針

- 調査や改善提案だけを求められた場合はファイルを編集しない
- 既存メモへの追記で足りる場合は、新規ファイルを増やさない
- 索引には一行説明を付け、リンク先を開く前に内容を判断できるようにする
- 用語集は短い索引として保ち、詳説をtopicsまたはusageへ移す
- 関連リンクは実際に内容がつながるものだけを追加する
- Markdownは`presswatch-markdown-style-ja`に従う
- API使用例を編集する場合は`presswatch-usage-notes-ja`に従う
- 用語集を編集する場合は`presswatch-glossary-ja`に従う
- timelineやtopicsの学習内容を編集する場合は`presswatch-notes-ja`に従う
- `notes/`がGit管理外の場合は、その状態を維持する

## 無断で行わないこと

- 多数のファイルの移動、改名、統合、削除
- timelineに残された歴史的記録の削除
- `notes/`をGit管理対象へ変更すること
- `notes/`の内容を`docs/`へ移すこと
- コードやGit管理対象のdocsの変更
- 個人メモ全体を機械的に短縮すること

ファイル移動や大規模統合が必要な場合は、対象、利点、欠点、リンクへの影響を示し、ユーザーの了承を得てから行う。

## 検証

変更後は、対象範囲に応じて次を確認する。

- 相対リンクの参照先ファイルが存在する
- 内部リンクの見出しが存在する
- 同じ見出しや用語項目を重複して追加していない
- コードフェンスの開始と終了が対応している
- 変更した行に不要な行末空白がない
- 現在の構成を説明するusage、topics、READMEに古い現在形が残っていない
- timelineの歴史的説明を現在形へ無理に書き換えていない
- `git status --short --branch`でGit管理対象の差分への意図しない影響がない
- `git check-ignore -v`で対象notesのGit管理外状態を必要に応じて確認した
- Git管理対象の差分がある場合は`git diff --check`が成功する

`notes/`がGit管理外の場合、`git diff --check`だけではnotesの書式を検証できない。

その場合は、対象ファイルへ`rg -n '[[:blank:]]+$'`を実行し、コードフェンスやリンクも別に確認する。

## 完了報告

次を簡潔に報告する。

- 新規作成、更新した索引とメモ
- 詳細説明の正本として残したファイル
- 削減またはリンクへ置き換えた重複
- 履歴として維持した説明
- 推奨する読む順番
- 実行した検証
- `notes/`がGit管理外かどうか
