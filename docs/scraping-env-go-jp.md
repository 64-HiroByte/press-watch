# 環境省報道発表スクレイピングメモ

確認日: 2026-08-29

## 対象

- 報道発表一覧: `https://www.env.go.jp/press/index.html`
- 利用条件: `https://www.env.go.jp/mail.html`
- robots.txt: `https://www.env.go.jp/robots.txt`

## robots.txt

- `User-agent: *`
- `Disallow: /cgi-bin`
- 今回の対象である `/press/index.html` と `/press/YYYYMM.html` 形式の月別一覧は、確認時点では明示的な禁止対象ではない。

## 利用条件の要点

- 環境省ホームページのコンテンツは、特記がない限り環境省に著作権が帰属し、権利表記がない限り[公共データ利用規約 第1.0版](https://www.digital.go.jp/resources/open_data/public_data_license_v1.0)が適用される。
- 利用時は出典を記載する必要がある。
- 編集・加工した情報を利用する場合は、出典とは別に編集・加工したことと主体を記載する必要がある。
- 環境省ホームページへのリンクは原則自由。ただし、環境省ホームページへのリンクであることを明記し、他サイト内に組み込まれるようなリンクは避ける。
- 将来 UI や API で取得データを表示する場合は、出典URLを保持し、必要に応じて「環境省ホームページをもとに作成」等の加工明記を検討する。

### 注記:

- 公共データ利用規約 第1.0版では、出典記載を条件として複製、公衆送信、翻訳・変形等の翻案、商用利用を含む二次利用が認められる
- 一方で、第三者の権利が含まれるもの、個別法令で制約されるもの、個別に別条件が示されるものは対象外または制限対象になり得る
- PressWatch では、詳細ページURLを保持し、表示や加工結果には出典と加工主体を追記できる前提で扱う。

## 一覧ページ構造

- 一覧本文は `p-press-release-list` 配下にある。
- 日付ごとに `details.p-press-release-list__block` があり、日付見出しは `span.p-press-release-list__heading` に `YYYY年MM月DD日発表` 形式で入る。
- 各発表は `li.c-news-link__item` の中にある。
- カテゴリは `span.p-news-link__tag` に表示される。
- 詳細ページリンクは `a.c-news-link__link` で、href は `/press/press_04490.html` や `/press/111118_00047.html` のような相対URL。
- 今回の最小実装では、`p-press-release-list__heading` から公開日を取得し、その日付見出し配下の `a.c-news-link__link` からタイトルと詳細ページURLを取得する。
- 取得元ページに表示されているカテゴリは、PressWatch独自カテゴリ分類とは分けて `source_categories` として保持する。
- 過去ページではカテゴリ表示がない報道発表が存在するため、DB 保存処理では `source_categories` の欠損を許容する。

## ページネーション構造

- 数字ページ送りではなく、月別一覧のリンク表で過去ページへ移動する構造。
- `h2` の「月別一覧」「過去の月別一覧」配下に `table.c-table-month__table` があり、月リンクは `a.c-table-month__col__link`。
- 月リンクの href は `/press/YYYYMM.html` 形式、`aria-label` は `YYYY年M月` 形式。
- 未来月などリンクがない月は `li` のみで、`a` が存在しない。
- 複数ページ巡回では、この月別リンクを収集して1ページずつ順次取得する。

## 巡回対象ページ

- 複数ページ巡回では、一覧ページ内の月別リンクを巡回対象として扱う。
- 月別リンクは `ArchiveMonthLink` として `year` / `month` / `url` を保持する。
- CLI の JSON 出力では、実HTTP巡回前に巡回候補を確認できるよう `archive_month_links` として出力する。
- 複数ページ巡回時は、`index.html` を月別リンクの取得元として扱い、報道発表データは月別ページから取得する。
- `index.html` の一覧には月初などに月をまたいだ発表が含まれる可能性があるため、巡回モードの主データには混ぜない。
- `parse_archive_month_links()` はHTML上の表示順を保って候補を返し、実際の巡回対象を選ぶ段階で `year` / `month` の降順に並べ替える。
- CLI では `--archive-month-limit` で取得する月別ページ数を明示し、指定件数だけ巡回する。
- 初回取得などで公開済みデータを順次取得したい場合は、`--all-archive-months` を明示したときだけ月別リンク候補をすべて巡回する。
- `--archive-month-limit` と `--all-archive-months` は意図が重なるため併用しない。
- `--from-file` は保存済みHTMLの単一ページ解析用とし、`--all-archive-months` とは併用しない。
- `--archive-month-limit 1` は、抽出された月別リンクのうち最新年月の月別ページ1件を取得する指定として扱う。
- 月別ページURLの重複取得は避け、月別ページ間で同じ報道発表が出た場合は詳細ページURLをキーに重複除外する。
- 実HTTP取得では、環境省サイトへの連続アクセスを避けるため、1回のscraper CLI実行内で連続するHTTP要求の開始間隔を3秒以上にする。
- 起点ページ、月別ページ、同一オリジンのredirect先は、実際のHTTP送信直前に同じrate limiterを通る。
- rate limiterは単調増加時計で前回の要求開始からの経過時間を測り、3秒に不足する時間だけ待機する。
- 取得失敗も要求を開始した事実として記録し、同じrate limiterを使う後続要求は3秒の不足分を待機する。
- 2026年8月28日の少数ページ確認で、起点ページと最新月ページの要求開始間隔が `3.005` 秒となることを確認した。
- 2026年8月29日の全件取得では、起点ページ1件と月別ページ359件の合計360要求を実行し、最後の要求を開始した時点の経過時間は `+1078.716` 秒だった。
  HTTPエラー、redirect、再開、再取得は発生しなかった。
- 将来自動リトライを導入する場合も、同じrate limiterを共有する。
- `fetch_press_page_html()` を複数回直接呼び出す利用側は、同じrate limiterを渡して共有する。
- この保証は1回のscraper CLI実行内を対象とし、複数プロセス間の開始間隔までは調停しない。
- 進捗確認が必要な場合は `--verbose` を明示し、要求番号、開始からの経過秒、対象URL、待機の残り秒数、月別ページ番号と対象件数を stderr に逐次出力する。
  stdout はJSON出力用として維持し、ターミナルで進捗だけを確認したい場合は `--no-stdout-json` と `--output` を併用する。
- 巡回結果には停止理由を含める。月別ページ数の上限に達した場合は `archive_month_limit_reached`、候補を最後まで取得した場合は `archive_month_links_exhausted`、既知の報道発表URLだけで構成される月別ページに到達した場合は `duplicate_release_detected` とする。
- ここでの既知URL集合は、呼び出し元が `known_release_urls` として渡す「すでに保存済み・取得済みとみなす報道発表詳細ページURL」の集合を指す。scraper 自身はDBを読み込まず、API側の取得・保存コマンドがDB内の最新公開月を含む直近3か月の `source_url` を取得し、`--known-release-urls-file` を通じて scraper CLI へ渡す。対象月数はAPI側の `--known-release-months` で変更できる。
- 異常終了時に失敗ページをスキップして継続する高度なエラーハンドリングは後続タスクで扱う。

## ローカル全件取得の途中保存

- `--crawl-state-dir PATH`は、ローカルで行う初回全件取得または件数を指定した検証巡回の途中保存に使用する。
- 巡回stateは本番へ配置せず、定期差分取得、実行履歴、長期保存、自動再試行の管理には使用しない。
- state利用時は`--all-archive-months`または正の`--archive-month-limit`を必須とし、`--from-file`と`--known-release-urls-file`は併用しない。
- 最終JSONはstateディレクトリ外の`--output`へ保存し、巡回全体が完了するまでは解析成功ページを含むHTMLを保持する。
- HTMLは`pages/index.html`と`pages/archive-NNNN.html`へ保存し、manifestには巡回条件、月別対象の確定状態、全体状態、停止理由、ページ別の取得・保存・解析状態、サイズ、SHA-256、UTC日時、失敗段階と理由を記録する。
- HTMLとmanifestは同じディレクトリ内の一時ファイルへ書き、`os.replace()`で原子的に置換する。
- stateディレクトリと`pages`は`0700`、manifestとHTMLは`0600`で作成する。
- manifestの日時は確認用であり、再開可否の判定には使用しない。
- SHA-256は保存HTMLの偶発的な欠損や破損を検出するために使い、改ざんを証明する電子署名としては扱わない。
- manifest利用前にversion、必須項目、型、列挙値、URL、ページIDとHTMLパスの対応を検証する。
- symlink、固定パスとの不一致、起点と異なるオリジン、不正URL、認証情報を含むURLを検出したstateは使用しない。
- `--resume`では取得失敗ページを再取得し、解析失敗ページは保存済みHTMLから再解析する。
- HTMLの欠損、サイズ不一致、SHA-256不一致、保存途中または保存失敗のページは通常再開で拒否し、`--refetch-invalid-pages`を明示した場合だけ再取得する。
- 起点ページを再取得した場合は、再解析した月別対象が既存manifestと年月、URL、HTMLパスまで一致するときだけ続行する。
- manifest破損、version不一致、巡回条件不一致、パス対応不一致は自動修復しない。
- 最終JSONの確認後は`--cleanup-crawl-state PATH`を使い、有効な`complete` stateだけを削除する。
- cleanupは削除前に全対象を検証し、symlinkや管理外ファイルなどを検出した場合は何も削除しない。
- stateは取得した公開ページ本文を含むGit管理外のローカル一時データとして扱う。
- 2026年8月29日の全件取得では、359件の月別ページをすべて解析し、34,421件の報道発表を含むJSONスナップショットを保存した。
  manifestと最終JSONの停止理由が`archive_month_links_exhausted`であること、JSONの件数と要素数が一致すること、詳細ページURLに重複がないことを確認してから巡回stateを削除した。

## 異常終了時の基本方針

- CLI の成功時は、`--no-stdout-json` を指定しない限り、取得結果を JSON として stdout に出力する。
- 取得結果をローカルで確認するだけなら、stdout をリダイレクトして一時JSONファイルとして保存する。
- 全件取得結果は再取得コストが高いため、取得件数や停止理由を後から確認するための検証用スナップショットとして、専用の `--output` オプションを利用できる。
- `--output` は本格的な保存機能ではなく、取得件数、URL重複、カテゴリ、停止理由を後から確認するための開発補助として扱う。
- `--output` 指定時は、同じJSONを指定ファイルにも保存する。
  `--no-stdout-json` を併用した場合だけ、stdoutへのJSON出力を抑止する。
- `--output` は取得とJSON生成が成功してからファイルを書き出す。
  途中で取得やJSON生成に失敗した場合は、途中結果を保存しない。
  ファイル書き込み後にstdoutへの出力だけが失敗した場合は、完成したスナップショットを残し、stderrと終了コード `1` でstdoutの出力失敗を伝える。
- `--output`では、追記保存、履歴管理、差分保存、圧縮、保存ディレクトリの自動生成を行わない。
- CLI の失敗時は、途中まで取得できたデータを JSON として出力せず、stderr に簡潔なエラーメッセージを出して終了する。
- stderr には、対象URL、`--from-file` や `--output` の対象パス、または `stdout`、例外種別、簡単な理由を含める。
- 例外理由は原則として `str(exc)` 相当の内容を使い、空の場合は `no detail` として扱う。
- 実行時エラーの終了コードは一律 `1` とする。引数エラーは argparse の既定どおり `2` とする。
- traceback は通常出さない。詳細なデバッグ出力が必要になった場合は、後続フェーズで `--debug` や logging 方針と合わせて検討する。
- 月別ページ取得中に1ページでも失敗した場合は、全体を停止する。失敗ページをスキップして継続する処理は現段階では実装しない。
- `stop_reason` は正常に巡回を終えた場合の停止理由に限定し、異常終了は stderr と終了コードで扱う。
- MVPの定期実行では、一時的な通信失敗に対する自動リトライを実装せず、失敗を確認して手動で再実行できる状態までを扱う。
  自動リトライの対象、回数、待機間隔、記録方法はMVP後に検討する。
- 将来リトライを導入する場合は、タイムアウト、一時的な通信失敗、HTTP 5xx を候補とし、404、HTML構造変更、パース異常、引数エラーは原則リトライ対象外として扱う。
- Phase 4 では、stdout を機械可読な実行結果、stderr を進捗・エラーとして使う既存方針を維持し、実行ログテーブル、実行ごとの自動ログファイル、本格的な logging 設定は追加しない。
  Phase 7 では既存の標準入出力とデプロイ先のジョブ結果・ログを使い、独自の永続的な実行ログはMVP後に検討する。

## 重複判定キー

- 現時点では、報道発表の詳細ページURLを重複判定キーとして扱う。
- 一覧ページから安定して取得できる情報のうち、タイトルや公開日は表記変更や同日類似タイトルの可能性があるため、詳細ページURLが最も一意性を期待しやすい。
- スクレイパーでは相対URLを絶対URLに正規化して保持し、DB 側でもこのURLを `source_url` として保存して一意制約を設ける。
- 将来、環境省側でより安定した公式IDが確認できた場合のみ見直す。
