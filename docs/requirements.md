# PressWatch - Requirements

## 1. 概要

PressWatch は、環境省サイト内の報道発表を定期取得し、一覧・検索・固定カテゴリによる絞り込みを通じて、必要な新着情報を効率よく確認できるようにするアプリである。

本ドキュメントでは、MVP時点の要件を整理する。

---

## 2. 機能要件

## 2.1 データ取得

### REQ-001: 報道発表一覧を取得できること

- 環境省サイト内の報道発表一覧ページから情報を取得できること
- 以下の情報を取得対象とする
  - タイトル
  - 公開日
  - 詳細ページURL
- 以下の情報は、取得可能であれば取得する
  - 分類情報

### REQ-002: 重複登録を防げること

- 同一の報道発表を複数回取得しても、DB上で重複登録されないこと
- 重複判定は、URLまたは外部一意キーを用いて行う

### REQ-003: 手動実行できること

- 初期段階では、開発者が手動でデータ取得を実行できること

---

## 2.2 データ保存

### REQ-004: 取得データをDBに保存できること

- 取得した報道発表データを PostgreSQL に保存できること
- `press_releases` は環境省の報道発表を原本に近い形で保存する共有データとして扱うこと
- 通常ユーザーは `press_releases` を直接作成・更新・削除しないこと
- `press_releases` の追加・更新は、管理者またはシステム実行のスクレイピング処理で行うこと
- MVP では、ユーザーが任意のタイミングでスクレイピングを実行し、共有データを書き換える機能は作らないこと

### REQ-005: 保存時刻を保持できること

- いつ取得したデータか分かるように fetched_at を保持すること

---

## 2.3 一覧表示

### REQ-006: 報道発表一覧を表示できること

- フロントエンドから、保存済み報道発表の一覧を表示できること
- 公開日の新しい情報から順に表示されること
- 一覧表示はページネーションに対応すること

### REQ-007: 一覧で主要情報を確認できること

- 一覧画面では最低限以下を表示すること
  - タイトル（詳細ページへのリンクを含む）
  - 公開日
  - PressWatch独自の固定カテゴリ

---

## 2.4 検索・絞り込み

### REQ-008: キーワード検索できること

- タイトルを対象にキーワード検索できること

### REQ-009: カテゴリで絞り込みできること

- 分野ごとに絞り込みできること
- MVP時点では、PressWatch 独自カテゴリによる絞り込みを前提とする
- MVPでは、旧 Topics Checker で使用していたCSVを初期データとする共有の固定カテゴリを使用する
- 旧CSVの水質カテゴリは、水道、環境水、排水の3カテゴリへ分ける
- カテゴリ定義と分類キーワードは責務を分けたCSVで管理し、分類結果は複数カテゴリを許容する中間テーブルへ保存する
- タイトルを正規化した部分一致で分類し、一致した固定カテゴリをすべて付与する
- 環境省ページから取得した分類情報は `source_categories` として保持するが、PressWatch 独自カテゴリとは分けて扱う
  再取得に時間がかかるため取得済みのデータとして保持し、画面の表示・絞り込みには使用しない。
- 固定カテゴリの初期データ、DB構造、取込方法、分類方法の詳細は `docs/fixed-categories.md` を正本とする
- Phase 5 では読み取り API を先行し、固定カテゴリの設計後にDB統合テスト、migration、取込、分類、カテゴリ絞り込みを順に実装する

---

## 2.5 定期取得

### REQ-010: 差分取得を定期実行できること

- 開発者が毎回手動で操作しなくても、通常の差分取得を定期的に実行できること
- 実行頻度と実行基盤は Phase 7 で決めること

### REQ-011: 定期実行の失敗を確認できること

- 定期実行が失敗した場合に、運用者がデプロイ先のジョブ結果、ログ、またはサービス標準の失敗通知から確認できること
- 実行履歴を検索・保持する独自機能はMVPに含めないこと

## 2.6 API

### REQ-012: 一覧取得APIを提供すること

- フロントエンドが `GET /press-releases` で報道発表一覧を取得できること
- 一覧は `published_at DESC, id DESC` の順で取得し、同じ公開日の順序を安定させること
- `page` は1始まりでデフォルト値を1、許容範囲を1から10,000とすること
- `page_size` はデフォルト値を50、許容範囲を10から100とすること
- `page` または `page_size` が許容範囲外の場合は、HTTP 422を返すこと
- レスポンスは `items` と `pagination` を持つこと
- `items` には `title`、`source_url`、`published_at`、`source_categories` を含めること
- `pagination` には `page`、`page_size`、`total_items`、`total_pages` を含めること
- データが0件の場合と最終ページを超えた場合は、HTTP 200と空の `items` を返すこと

#### Phase 6の一覧レスポンス拡張

Phase 6-4で設計・合意した以下の契約はPhase 6-6で実装済みである。
全所属・表示順・所属なし・照会回数・DB非更新は、合成データを使うテスト専用PostgreSQL 17で検証済みである。

- 既存公開フィールドを維持し、各記事へ`fixed_categories`を追加すること
- `fixed_categories`は`slug`・`name`を持つ要素の配列とし、保存済みの全所属を表示順で返すこと
  検索で指定したカテゴリだけに限定せず、所属なしは`[]`を返し、`null`やフィールド省略にしない。
  `display_order`や数値のカテゴリID・分類キーワードは公開しない。
- `source_categories`は削除せず、Webでは表示・絞り込みに使用しないこと
- 表示部品の都合だけで公開記事IDを追加しないこと

取得方式と照会上限は[固定カテゴリのPhase 6設計](fixed-categories.md#phase-6のカテゴリ取得設計)を正本とする。

#### 一覧・検索APIのエラー応答

`GET /press-releases`のDB関連エラーは、正常な空一覧へ置き換えず、次の`application/json`で返すこと。

| 条件 | HTTPステータス | 応答 |
| --- | --- | --- |
| SQLAlchemyの`TimeoutError`、または`DBAPIError.connection_invalidated`が`True` | 503 | `{"detail":"Service unavailable"}` |
| その他のSQLAlchemy例外、DB設定・初期化・Session終了の失敗 | 500 | `{"detail":"Internal server error"}` |

- 例外本文やSQLSTATEによる追加分類、自動リトライ、`Retry-After`は追加しないこと
- routeの想定外例外やレスポンスDTOの検証失敗は、DB関連エラーへ変換せず、既定のHTTP 500と`text/plain`を維持すること
- Session生成後の正常終了・通常の例外終了では、応答送信前にcloseを1回試みること
  closeだけが失敗した場合は上表に従い、処理中の例外もある場合は元の例外を優先すること。
- 入力検証エラーとclose失敗が重なった場合は、元のHTTP 422と既存の形式を返すこと
  Session初期化は入力検証より先に行われるため、この段階の失敗では入力が不正でも上表のエラーを返すこと。
- DB関連エラーの応答と今回のアプリ診断には、元の例外本文、SQL、parameters、接続情報、秘密情報、報道発表の入力値を含めないこと
  アプリ診断は固定イベント名をstderrへ出力し、書込・flushの失敗を再試行せず、HTTP応答や元の例外を置き換えないこと。
- OpenAPIの500にはDB関連の`application/json`と既定の`text/plain`を、503には固定JSONを記載し、既存公開フィールドと422の形式を維持すること
  Phase 6の200 schemaには、上記の`fixed_categories`を追加する。

503で復旧や再試行の成功を保証しない。
キャンセル・プロセス終了時の即時closeやclose成功、アクセスログ・SQLAlchemy内部ログ・ホスティング基盤を含む全ログの非露出は、このエラー処理の保証対象に含めない。

### REQ-013: 検索・絞り込みに対応したAPIを提供すること

- キーワードやカテゴリを指定して一覧取得できること
- `GET /press-releases`の任意の`q`でタイトルを検索できること
- `q`は100文字までとし、100文字を超える場合はHTTP 422を返すこと
- 文字数上限は前後空白を除去する前の`q`へ適用すること
- `q`の前後空白を除去し、空文字列または空白だけの場合は検索未指定として扱うこと
- `q`にNUL文字が含まれる場合はHTTP 422を返すこと
- タイトル検索は、大文字小文字を区別しない部分一致とすること
- `%`や`_`を含む検索文字列は、SQLのワイルドカードとして解釈せず、入力された文字として検索すること
- 検索条件に一致する件数と報道発表一覧へ同じ検索条件を適用すること
- 任意の`fixed_category`で、保存済みの固定カテゴリ分類結果から絞り込めること
- カテゴリはslugで指定し、`fixed_category=air&fixed_category=soil`のような同名クエリの繰り返しをOR条件として扱うこと
  カンマ区切りはHTTP 422とし、カテゴリ間のAND指定機能は提供しない。
- カテゴリは20指定まで、各値は前後空白を除去する前に100文字までとし、上限超過はHTTP 422を返すこと
  指定数の上限は空要素・重複を除去する前に適用する。
- 各値の前後空白を除去し、空要素と同じslugの重複を除外すること
  未指定または全要素が空の場合は、未分類を含む従来の一覧・検索を維持する。
- 空白除去後の非空の値は`[a-z][a-z0-9]*(?:_[a-z0-9]+)*`への完全一致を要求し、不正な値が一つでも含まれる場合はHTTP 422を返すこと
  大文字小文字変換やNFKC正規化は行わない。
- 形式が正しい未定義slugは一致なしとして扱い、既知slugとの混在時は既知の一致分だけを返すこと
  すべて未定義の場合やカテゴリ定義が未投入の場合はHTTP 200・0件とし、DB障害は既存の500・503応答へ伝える。
- カテゴリのOR条件とタイトル検索条件はANDで組み合わせ、複数カテゴリに属する報道発表も一覧・件数では1件として扱うこと
- 絞り込み後もREQ-012の新着順・ページ条件・公開項目・0件と超過ページの扱いを維持すること
- 一覧要求ではCSV読込み・タイトル分類・seed・再分類・データ更新を行わないこと

#### Phase 6の公開日範囲検索

Phase 6-4で設計・合意した契約をPhase 6-6で実装済みである。
日付境界・片側・未指定・条件の組合せ・ページ送り・照会数・DB非更新は、合成データを使うテスト専用PostgreSQL 17で確認済みである。

- `GET /press-releases`の任意の`published_from`・`published_to`で公開日を絞り込めること
- 日付は`YYYY-MM-DD`の実在する日付とし、下限・上限の両端を含むこと
- APIへ片側だけ指定した場合は、その側だけを制限し、両方未指定なら公開日を制限しないこと
- 不正な形式・存在しない日付・下限が上限より新しい指定はHTTP 422を返すこと
  逆順指定のエラー位置は既存422形式の`loc`を`["query", "published_to"]`とする。
- 日付・タイトル・カテゴリの条件はANDで組み合わせ、件数と一覧へ同じ条件を適用すること
  カテゴリ間のOR、新着順、既存ページ条件、0件・範囲外ページの契約は維持する。

Webは検索時に日付の順序を揃え、開始日だけなら日本時間の今日を終了日としてAPIへ送る。
API単独の境界指定と、Web入力の補助・具体化を分け、APIで今日や最古日を補完しない。
入力欄・URL・プリセットの操作は[一覧の操作・状態仕様](frontend-ui.md#一覧の操作状態仕様)を正本とする。

### REQ-014: 固定カテゴリの選択肢を取得できること

Phase 6-4で設計・合意した契約を、Phase 6-6の最初の小タスクで実装済みである。
表示順・正常0件・1 SELECT・DB非更新は、合成データを使うテスト専用PostgreSQL 17で確認済みである。

- `GET /fixed-categories`は`{"items":[{"slug":"air","name":"大気","display_order":1}]}`形式で保存済みの定義を返すこと
- 要素は`display_order`の昇順とし、数値IDや分類キーワードを公開しないこと
- 定義が未登録の場合はHTTP 200と`{"items":[]}`を返すこと
  テーブル未適用・権限不足・接続障害を正常0件に置き換えない。
- 既存の共通DBエラー処理とSessionの終了・例外優先順位・秘匿方針を使用すること
  想定外例外は既定の500として扱い、自動再試行を追加しない。
- 定義を1回のSELECTで取得し、CSV読込み・seed・再分類・データ更新を行わないこと

定義0件でもAPIの未絞り込み一覧・タイトル検索を停止しない。
Webの操作停止は[状態表示の仕様](frontend-ui.md#取得中失敗空状態)として区別する。

## 4. MVPの範囲

## 4.1 MVPで実装するもの

- 環境省報道発表一覧の取得
- DB保存
- 一覧表示
- キーワード検索
- 共有の固定カテゴリによる絞り込み
- 通常の差分取得の定期実行
- 定期実行の失敗を運用者が確認するためのジョブ結果、ログ、またはサービス標準の失敗通知
- 公開APIの入力値とリクエスト数の制限

## 4.2 MVPでは実装しないもの

- ユーザー認証
- 複数ユーザー管理
- ブックマーク
- ユーザー定義カテゴリ
- 利用者向けのメールによる新着通知
- AI要約
- 複数省庁対応
- 管理画面の作り込み
- 高度な全文検索
- 権限管理
- 保存済みレコードの内容変更を確認するメンテナンス用フルスキャン

## 4.3 現在の実装段階

Phase 3 では、MVP のうち DB 保存の土台として、PostgreSQL 接続、`press_releases` テーブル、Alembic migration、DTO / repository / service 経由の保存処理、通常の重複 skip までを扱う。
Phase 4 では、scraper CLI からDB保存までを接続する手動取得・保存コマンド、初回全件取得、通常の差分取得を実装済みである。
通常の差分取得では、DB内の最新公開月を含む直近3か月の `source_url` を既知URLとして使い、保存済みURLだけの月で巡回を停止する。
通常取得では保存済みレコードの内容を更新しない。
タイトル、公開日、取得元カテゴリなどの変更を確認するメンテナンス用フルスキャンは MVP後の改善候補とする。
定期実行と、運用者が失敗を確認するためのジョブ結果、ログ、またはサービス標準の失敗通知は Phase 7 で扱う。
実行履歴の検索、長期保存、再試行管理などの本格的な運用機能は MVP後の改善候補とする。
Phase 5 開始前の見直しで、管理 PostgreSQL に Supabase を採用し、PostgreSQL 18 の初期方針から 17 へ変更することを決定した。
ローカル環境の PostgreSQL 17 への変更、Supabase への Direct connection、既存 Alembic migration の `9f2c7a4e1d63` までの適用を確認済みである。
Data API は利用せず、Supabase の `anon`・`authenticated` ロールが `public.press_releases` の `SELECT` 権限を持たないことを2026年8月20日に確認済みである。
この結果は現時点の確認であり、Data API や Supabase Auth の採用時、権限や migration の変更時、Supabase プロジェクトや DB の再作成時、本番公開前には再確認する。
Phase 5 では、ヘルスチェック、一覧取得、新着順、ページネーション、タイトル検索、固定カテゴリ絞り込みの読み取り API を実装済みである。
独自カテゴリは、旧 Topics Checker のCSVから正規化し、水関連分野を見直した初期データを使う共有の固定カテゴリとして実装済みである。
固定カテゴリの3テーブル、seed CLI、新規保存時の分類、既存報道発表の再分類CLIを実装し、テスト専用PostgreSQL 17で検証済みである。
開発DB・Supabaseへの固定カテゴリmigration適用・seed実行、および実データの再分類は未確認であり、コードの実装完了と区別する。
ブックマーク、ユーザー登録、ユーザー定義カテゴリは MVP後に扱う。
ユーザー認証と複数ユーザー管理は、引き続き MVP では実装しない。
フロントエンド画面は Phase 6 以降で扱う。
Phase 6では、依存関係の更新とUI基盤の導入後に固定データのMockを確認し、操作・API設計と検証基盤を整えてから機能を実装する。
固定カテゴリの選択肢取得APIはPhase 6-6の最初の小タスクで実装し、テスト専用PostgreSQL 17で検証済みである。
一覧レスポンスへの記事ごとの固定カテゴリ情報追加とN+1防止も実装し、合成データを使うテスト専用PostgreSQL 17で検証済みである。
公開日範囲検索APIも実装し、日付境界と条件の組合せ・ページ送りを合成データのテスト専用PostgreSQL 17で検証済みである。
Web接続と接続検証用の常設DB準備は後続タスクで扱う。
これらのAPIの詳細な契約はPhase 6-4で確定済みであり、要件と固定カテゴリ設計に記録した。
既存APIの`source_categories`は維持し、画面側で使用しない。

## 6. 想定データ項目

Phase 3 初期では、まず環境省から取得した報道発表の原本に近いデータを保存する。
共有の固定カテゴリは、APIのカテゴリ絞り込み実装前に初期データ、DB構造、取込方法、分類方法を設計済みである。
`press_releases` はアプリ全体で共有する原本データとして扱い、固定カテゴリの分類データとは分けて設計する。
ユーザーごとのブックマーク、メモ、ユーザー定義カテゴリ、通知条件などはMVP後に別データとして設計する。

### press_releases

- id
- title
- source_url
- published_at
- source_categories
- fetched_at
- created_at
- updated_at

`source_categories` は環境省ページに表示された取得元カテゴリであり、過去ページではカテゴリ表示がない報道発表が存在するため欠損を許容する。

### Phase 5で実装するデータ

- 独自カテゴリ
  - 旧 Topics Checker で使用していたCSVから正規化した初期データを、共有の固定カテゴリとして扱う
  - 旧CSVの水質を水道、環境水、排水へ分け、合計10カテゴリとする
  - カテゴリ定義、分類キーワード、報道発表との多対多分類結果を分けて保存する
  - タイトルに一致したすべての固定カテゴリを付与し、分類結果をDBへ保存する
  - `press_releases` の原本データとは分けて設計する

固定カテゴリの詳細は `docs/fixed-categories.md` に整理する。

### MVP後に検討するデータ

- bookmarks
  - ユーザー登録と利用者単位の扱いが決まってから設計する
- ユーザー定義カテゴリ
  - ユーザー登録と利用者単位の扱いが決まってから設計する
