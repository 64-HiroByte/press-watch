# PressWatch - Tasks

## 方針

- 1タスク = 1責務 を意識する
- 各タスクはレビューしやすい粒度に分ける
- まずはMVP完成を優先する
- いきなり全部作らず、土台 → データ取得 → 保存 → API → 画面 の順で進める
- Codex には小さな単位で依頼し、差分ベースでレビューする

この文書には作業項目、進捗、完成条件、未対応事項を記載する。
チェック済みは、作業の実施だけでなく、対応する完了条件を確認したことを表す。
完了後の詳しい実施記録や判断経緯は関連docs・notesへ整理し、ここには必要な参照先を残す。

## Phase 6: フロントエンド実装

画面の表示・絞り込みにはPressWatchの固定カテゴリを使い、環境省の取得元カテゴリは再取得の手間を避けるため保持するが画面では使用しない。
採用技術とバージョン更新候補は[技術構成](tech-stack.md)、製品要件は[要件定義](requirements.md)を参照する。

- MVPの画面確認は業務用PCを中心とし、スマートフォン専用の作り込みはPhase 6の完成条件に含めない。
- Mockは固定データによる表示確認とし、API接続や検索・絞り込みの処理は後続タスクで実装する。
- Mock確認後に操作・API仕様を記録・合意し、機能実装前にOxlint・Oxfmtと検証基盤を整える。
- 機能ごとに実装・テスト・レビューまで完結させ、ローディング・エラー・空状態を最後へ先送りしない。
- 認証・ブックマークなどのMVP外機能は追加せず、デプロイと定期実行はPhase 7で扱う。

API追加と機能実装では、テストを先に追加し、未実装による失敗を確認してから実装する。

## Codexへ依頼する時の基本ルール

- 一度に大きく作らせすぎない
- 1回の依頼で1責務に絞る
- 差分ベースでレビューする
- 要件にない機能を勝手に広げない
- 不要なリファクタを避ける
- 何を作るか、何を作らないかを毎回明示する
- 対象Phaseブランチとの差分で確認しやすい単位を保つ
