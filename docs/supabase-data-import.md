# Supabaseへの保存済み実データ投入

## 目的と前提

ローカルで検証した保存済み原本を、本人向け限定配置で使用するSupabaseへ投入するための準備・適用・検証・復旧方針を定めます。
この文書は実行承認を兼ねません。
実行時は対象・現況・操作・影響を具体化し、下記の段階別承認を得ます。
実サイトからの再取得、取得ジョブの配置・定期実行、一般公開、性能改善、依存更新・再配置は含めません。

原本保持と環境間照合の契約は、[永続開発DBでの確認](local-development.md#永続開発dbで実データを確認する)を正本とします。
既存の[DB migration方針](db-migrations.md#実行方針)と[限定配置のDB接続](deployment.md#限定配置のdb接続)を併用します。

## 投入対象と照合基準

| 項目 | 基準 |
| --- | --- |
| 保存済みJSON | `tmp/env-press-full-crawl-20260829/env_press_all.json` |
| SHA-256 | `742ec50a03c4b69e8fc88fccd8a95856a94a18d895717c9a6834bcae144d3939` |
| 原本 | 34,421件、URL重複なし |
| 公開日 | 1996-11-01〜2026-08-28 |
| 共通の取得日時 | `2026-08-29T13:45:27.408274Z` |
| カテゴリ定義 | 同梱CSVの10カテゴリ・57キーワード |

JSONを原本として変更せず、既存の`load_validated_snapshot`で件数・ハッシュ・構造・URL・保存DTOを検証します。
既存の`to_press_release_creates`で変換し、空の取得元カテゴリ2,678件はNULLとして保持します。
取得日時を投入時刻で置き換えません。
ファイルまたは原本集合が基準と異なれば、Supabaseへ進まずローカルでの準備・再検証へ戻ります。

環境間では`source_url`をキーに、タイトル・公開日・取得元カテゴリ・取得日時を全件比較します。
ID・作成日時・更新日時の環境間一致は要求しません。
投入直後には対象DBの原本全8列と連番を基準として記録し、分類前後の全8列の不変を確認します。
連番の欠番を不整合とせず、連番をリセットしません。

## 準備段階

### 接続とツール

実行プロセスは親の`DATABASE_URL`・`PG*`を継承せず、承認した対象の接続情報とCAだけを渡します。
ローカルDB用、Supabase管理用、API読取り用の接続情報を分離し、各操作の直前に接続先を照合します。
SupabaseはDirect connectionと`sslmode=verify-full`を維持し、CAとホスト名を検証します。
到達できない場合は停止し、pooler・接続方式・配置地域を自動変更しません。

秘密値は本人の安全な非表示入力で対象プロセスへ渡し、コマンド引数・履歴・ログ・文書へ残しません。
秘密ファイルは、対象と用途の明示許可なく読みません。
SQLパラメータや生の接続例外を表示せず、診断は処理段階と秘密値を含まない結果に限定します。
管理資格情報を常時稼働するAPIやWebへ渡しません。

既存の隔離配置済みPostgreSQL 17系クライアントを優先し、`pg_dump`・`pg_restore`・`psql`の実体と版を確認します。
DBの現行版との互換性を確認し、常用クライアントの更新やPATHの変更を避けます。
クライアントの存在や版確認を、接続・バックアップの成功と混同しません。

### 読取り診断

過去のローカル検証・限定配置の結果を、現在の対象DBの状態と断定しません。
次の項目を両DBについて確認し、基準と照合します。

| 項目 | 確認内容 |
| --- | --- |
| 対象 | 接続先、DB・ユーザー・schema、PostgreSQL版、ローカルDBのコンテナ・永続化先 |
| schema | revision、業務4テーブルと`alembic_version`、全列・主キー・一意制約・外部キー・CHECK・索引 |
| 原本 | 全件のURL・内容、件数・日付範囲、原本全8列、連番の定義・状態と最大IDとの整合 |
| 分類 | CSVとの定義一致、全所属、原本と分類の参照整合 |
| 書込み | 取得ジョブ・手動処理等の有無、他のトランザクション・書込みロック |
| DB公開面 | Data APIの無効化、RLS、`anon`・`authenticated`の原本SELECT権限がないこと |
| 権限 | 所有者、ACL、デフォルト権限、ロール属性・所属・設定、`PUBLIC`・継承による実効権限 |
| API専用ロール | 既存の読取り権限・接続数・期限設定との一致、管理・所有・書込み権限がないこと |

API専用ロールの基準は[限定配置のDB接続](deployment.md#限定配置のdb接続)に従います。
管理接続や`service_role`はRLSを回避できるため、RLSだけを安全性の根拠にしません。
想定外のschema・データ・権限があれば止め、修正を診断の一部として実行しません。

### バックアップと隔離復元

保存先はGit管理外の`tmp/supabase-real-data/`配下の新規実行ディレクトリとします。
ディレクトリは700、バックアップ・基準データ・診断記録は600で新規作成し、既存ファイルを上書きしません。
過去タスクのバックアップは今回の承認に含めず、内容を開いたり再利用したりしません。

対象DBのcustom形式バックアップを取得します。
対象schema・依存・取得可能な範囲は現況診断から具体化し、必要な復旧対象を収録できない場合は停止します。
原本・分類だけを変更する場合に`public` schema限定のバックアップを使うときは、業務4テーブル・revision・連番・依存定義・権限の収録を確認します。
Auth等の管理用schemaを含まないことと復旧できる範囲を報告し、必要な復旧対象が範囲外にある場合はそのまま進めません。
終了状態、サイズ、SHA-256、TOC、原本・定義・所属・revision・連番・必要な依存定義の収録を検査します。
`pg_restore --exit-on-error --file=/dev/null`による全体読取りと、実際の復元試験を別に記録します。
通常の`pg_dump`にロール定義・所属は含まれないため、ロール属性・所属・所有者・ACL・設定を秘密値なしで別記録にします。

復元先は既存DB・ボリュームを共有しない専用PostgreSQL 17コンテナとします。
起動前に承認済みローカルDocker daemonのendpointを照合し、起動・復元・停止を同じcontextへ明示固定します。
接続先不一致では停止し、リモートdaemonへバックアップを転送しません。
ホスト接続が必要な場合だけ`127.0.0.1:55434`へ公開し、使用中なら既存処理を終了させず停止します。
使用イメージ・専用コンテナ名・データ保持先・空き容量を起動前に照合し、イメージや容量不足を無断取得・削除で解消しません。

業務4テーブル、revision、連番と必要な依存定義・権限を復元します。
必要なロールは隔離先に秘密値なしで用意し、復元対象の選択と依存関係を事前レビューします。
全列・制約・索引・定義・全所属・連番・権限を取得元の基準と照合し、依存不足や復元エラーを無視しません。
この試験を、Supabase管理schemaやサービス全体の再現・復旧の保証とは扱いません。

### 一時投入手順の事前検証

既存の`load_validated_snapshot`・DTO変換・原本用`create_press_releases`・再分類処理を利用する一時手順を作成し、適用承認前にレビューします。
前回のローカル用一時手順は旧revision・特定環境に固定したものであり、そのままSupabaseへ実行しません。
今回の接続先・revision・空DB確認・ロック・タイムアウト・エラー処理・停止方法を具体化します。
適用時のホストは今回のバックアップ取得先の照合記録へ固定し、接続前にdriver・ホスト・ポート・DB・ユーザー・許可した接続オプションを検証します。
ローカル試験用の接続と、証明書・ホスト名検証を必須にするSupabase接続を区別し、実接続後にもidentityを照合します。

同じ隔離環境内の試験用DBを使い、復元照合の証跡を保持して次を確認します。

- 基準JSONを正常投入し、全内容が一致する。
- 後続バッチで失敗したとき、原本INSERT全体がrollbackされる。
- 接続先不一致や想定外の既存行を、書込み前に拒否する。

試験ごとの開始状態と接続先を固定し、試験用DBを本番接続先へ切り替えたまま試験しません。
原本repositoryはcommit・rollbackを管理しないため、一時手順が全件のトランザクションを管理します。
連番消費はrollbackされないため、欠番を許容して連番を戻しません。
汎用CLIや新しいテスト基盤は作りません。

### 費用・容量・準備結果

Supabaseの実プラン・残容量・通信量と、ローカルDBのテーブル・索引サイズを対応付け、投入後の容量を見積もります。
JSONサイズを必要DB容量とみなさず、バックアップ通信、復元先の容量、今回の検証に必要な通信も確認します。
DBサイズの利用枠と、WAL・一時ファイル等を含む物理ディスクの占有は区別し、現行の公式条件と対象環境の使用量を照合します。
本人がRailwayのTrial残量・期限・利用額・通知と停止設定を確認します。
DBの休止とRailwayの停止・再開を区別し、動作確認を完了できる条件と復旧上の制約を報告します。

約1週間の利用量評価、継続バックアップ頻度・保管先・復元確認、有料移行は未完了事項として残します。
今回のバックアップはローカル保管であり、同一ディスク故障への備えや継続運用のバックアップを完了したとは扱いません。
既知のセキュリティ問題は投入経路への影響を確認し、判断に必要な未確認事項を適用前に解消します。
必要な依存更新・再配置を自動追加せず、影響と別の対応範囲を報告します。

準備結果として、現況、使用コード・ツール、バックアップ検査、隔離復元、一時手順の検証、実行可能条件・制約・未確認事項を提示します。
必要なDB書込み・API／Web利用・停止／復旧手順を具体化してから、適用段階の別承認を得ます。

## 適用段階

### 通常経路の条件

Supabaseの原本が0件、revisionが`a51eab6808f3`、カテゴリ10件・キーワード57件がCSVと完全一致する場合、migration・seedは省略します。
想定外の既存行、schema、定義・所属・権限があればそのまま進めません。
必要なmigration・seed・権限変更等を具体化して計画と承認を更新し、適用済み処理を無条件に再実行しません。

### 適用直前の確認と投入

1. 本人へ作業開始と画面操作を控える期間を伝えます。
   Webの未認証・不正認証がチャレンジ付き401で拒否されること、保護する応答の`private, no-store`、記事一覧HTML・RSC等の既存保護対象、APIに公開ドメイン・TCP Proxyがないことを確認します。
   不一致なら投入しません。
2. 他の書込みを停止し、接続先・revision・原本・定義・所属・権限・連番を再照合します。
   直前バックアップを新規取得・検査し、準備時から復旧対象の状態が変化していれば隔離復元試験も更新します。
3. 基準JSONを再検証し、承認した一時手順で原本repositoryへ最大1,000件ずつ渡します。
   同一トランザクション内で競合防止ロックを取得して原本0件を再確認し、全件を保存します。
   保存34,421件・skip0件と全内容の一致を確認してからcommitします。
4. 別の読み取り専用接続でも照合し、投入直後の原本全8列・連番を基準として保持します。
   再分類前バックアップを取得・検査してから、既存の`reclassify_fixed_categories`で全件を再分類します。
5. 原本全8列の不変、全定義・全所属・連番・権限を確認します。
   配置SHAを記録したRailway内部APIと既存Webで動作を検証し、Webの認証拒否とAPIに公開経路がないことも再確認します。

既存URLの置換・削除、連番リセットは行いません。
原本commitから分類・照合の完了までは不完全な分類が表示され得るため、本人は確認開始の報告後に画面操作を再開します。
失敗時は未完了状態として報告し、メンテナンス画面の実装は追加しません。

## 停止と復旧

接続先・原本・revision・権限・定義・Docker接続先の不一致、想定外の既存行、バックアップ・復元・事前検証の失敗では停止します。
エラー時は後続書込みを止め、実際のcommit状態を読み取りで確認します。
CLI終了コードだけで未保存と判断せず、自動再投入しません。
原本投入・migration・seed・再分類はそれぞれのトランザクション境界を持ち、全段階が自動で投入前へ戻るとは扱いません。

復旧が必要なら、復旧先・使用バックアップ・ロールと権限の記録・失う可能性のある変更を提示して別承認を得ます。
隔離先で確認してから元DBへの復元・切替を判断し、古いバックアップで後続の変更を無条件に上書きしません。
DROP・TRUNCATE・全体復元・downgrade・DB再作成・ボリューム削除・所属削除・連番リセットは自動実行しません。
認証迂回や情報露出時は[限定配置の停止・復旧方針](deployment.md#検証と停止復旧)に従い、必要な外部操作を別途確認します。
